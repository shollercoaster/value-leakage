**Experiment 9 GPU-hours (tracked separately, per the note above — not added to the running total column):** RunPod H200, no cached pod/volume from the original Experiment 7 session existed, so this ran the full "fresh pod" path in `EXPERIMENT_9_RUNBOOK.md`. Real events, not estimated: (1) initial ~127GB model download failed at 43GB on `Disk quota exceeded` — the attached RunPod network volume's own provisioned size was smaller than the checkpoint, a fact invisible to `df`/`stat` from inside the pod since those report the shared backend pool's totals, not this volume's quota; stopped and asked the applicant to resize it via the RunPod dashboard (no in-pod access to do this — one read-only query to RunPod's REST API for the volume/pod size was attempted and got HTTP 403, so no further attempts were made with live credentials) rather than guessing around it; (2) after the resize, the download resumed from the 14 already-downloaded shards and completed (39/39 shards, 119GB); (3) three real dependency/compatibility gaps surfaced and fixed live, none of them the two workarounds `FINDINGS.md`'s Experiment 7 entry documented: `accelerate` was missing entirely (`pip install accelerate`); the Triton finegrained-fp8 fallback kernel (the path `TRANSFORMERS_DISABLE_DEEPGEMM_LINEAR=1` correctly routes to) needed `kernels==0.16.0`, not installed by default; and that hub-fetched kernel's own `bayesian_autotuner.py` imports four names (`JITFunction`, `get_cache_manager`, `triton_key`, `get_cache_invalidating_env_vars`) that this triton version (3.4.0) no longer re-exports from `triton.runtime.autotuner` — traced each to its real defining module and added a narrow import-location shim in `jlens_experiment9.py` (no fp8 math touched). (4) A real, independently-caught bug: the `diagnose` stage's own plain-logit-lens layer numbering was one-indexed while `jacobian-lens`'s own layer convention (confirmed by reading `jlens/lens.py` directly) is zero-indexed — left uncorrected, every lens-vs-plain-control "layer of first prominence" comparison in the eventual write-up would have been silently off by one layer. Fixed before the paid `read` stage, not after. Wall-clock directly observed across setup, the failed download, the resize wait, dependency debugging, and the real `diagnose`/`read`/`plot` runs: at least ~30-45 minutes (a precise figure isn't available since the RunPod dashboard resize happened outside any in-pod tool call I can timestamp) — at $3.59-4.59/hour (Community/Secure Cloud), call it **~$2-3.50**, not the $10-15 dollar ledger above. The download-and-fix time was real overhead beyond the ~1 hour analysis target `EXPERIMENTS_NEEL_NANDA.md` §2.2 sets for Experiment 9 itself, but the actual `diagnose`/`read`/`plot` sequence once dependencies were sorted took only a few minutes of GPU time (model loads in ~40s from local disk; the six lens reads and four plots are each seconds), so the 1-hour analysis target itself was not at risk.
